# asm skill P1-2：文本类别进索引（`messages.kind`、thinking 入库、schema 5）

## 做了什么

- `model.rs`：新增 `TextKind { Prompt, Reply, Thinking, Other }`（`as_str` / `parse`，serde 用小写），`MessageRow` 加 `kind`。一条 assistant 记录同时有 thinking 和 text 时写成两行，同一个 `byte_offset`，thinking 在前。
- `schema.sql`：`messages.kind TEXT NOT NULL CHECK (...)`；`messages_fts` 加 `kind UNINDEXED`，两个触发器同步写入。触发器的 `is_meta = 0` 条件不变。`db.rs`：`insert_messages` / `messages()` 加列，`messages()` 改成 `ORDER BY byte_offset, id`（同一行的两条按写入顺序）；新增 `Db::user_uuids`。
- 一份判断（`transcript.rs`）：`UserFlags { is_meta, is_compact_summary, origin, interrupted }` 是判断所需的最小输入，`transcript::Record` 和 `parse::RawRecord` 各写一个 `user_flags()`。`is_human_input` / `is_interruption` 改为接收它，新增 `opens_turn = is_human_input && !is_interruption`。导出用 `opens_turn`，`conversation.rs` 照旧先判中断再判人类输入，结果等价。`RawRecord` 补了 `isCompactSummary`、`origin.kind`、`interruptedMessageId` 三个字段。
- `parse.rs`：
  - `on_user`：满足以下全部条件时 `kind = Prompt`，否则是 `Other`：不是 sidechain、uuid 没出现过、`opens_turn`。prompt 计数等 `delta` 逻辑完全不变（仍是 Python 的口径）。
  - `on_assistant`：trim 后非空的 thinking 块用 `\n` 拼成一行 `Thinking`，`assistant_msg_count`、`last_message` 只看 text，不变。
  - 预过滤：`user_line_may_have_text` 不变，另加 `user_line_has_media_prompt`：行里没有 `"tool_use_id"`，并且有 `"type":"image"` 或 `"type":"document"`，才放行去解析。`classify` 没改。
- `indexer.rs`：对 `Plan::Append` 的会话文件，先在主线程取出已索引的 user uuid，交给 `TranscriptParser::seen_user_uuids`。
- `fts.rs`：`FtsRoles` 内部换成 kind 列表；`count_per_session` 由 `m.role IN` 改为 `m.kind IN`，FTS 和 LIKE 两条路径都一样。
- fixture：S3 的第一条回复加了带正文的 thinking 块，另加一条 `origin.kind = task-notification` 的通知、一条 `compact_boundary` 和一条 compact 摘要。S1 原本已有带正文的 thinking、只有签名的 thinking 和只贴图片的输入。`uv run` 重新生成后只有 S3 的 jsonl 变了。`gen_fixtures.py` 的 diff 里其余部分是编辑后 hook 自动格式化（`reader_rows` / `conversation_rows` 改了换行），生成结果没有变。
- 文档：`skills/asm/references/cli.md` 的 `other` 一行写明中断标记归 other、本地命令输出算 prompt，transcript 阅读模式的 `<other>` 说明同步修改（决定 6，同一提交）。`kb/docs/claude-session-data-format.md` 在「判定人类输入的消息」后补了一段，说明回合编号 / `prompt` 的口径和计数口径的区别。

## 自己的决定

1. prompt 的口径是「回合编号会加一的 user 记录」：`opens_turn` 加上「不是 sidechain」「uuid 第一次出现」（`read_conversation` 在判断前就跳过这两种）。中断标记归 other，这和协调者 2026-11-15 转来的审阅意见一致，计划 `session-search.md:172` 写的「⇔ `is_human_input`」不够准确。
2. 重复 uuid 要在增量时也算对：解析器记下已写入的 user 行 uuid；追加扫描时，indexer 从库里取出这个会话已有的 user uuid 交给解析器（`Db::user_uuids`，每个追加的文件查一次）。这样「全量 == 多次增量」对 kind 也成立（有测试）。真实数据里重复 uuid 的人类输入是 0 条（`dup_uuid.py`），做这件事只是为了让口径完全一致。
3. 只贴图片 / 文档、没有文字的输入：回合会加一，所以写一行文本为空的 prompt，保持计数和回合一致（Python 口径的 prompt 计数不变）。为此加了 `user_line_has_media_prompt` 预过滤；tool_result 带的截图在开头几个字节就会遇到 `tool_use_id`，所以排除它们几乎不花时间。真实数据里这种输入是 0 条（`media_prompts.py`，72 条带图片的人类输入都有文字），只有 fixture 覆盖。
4. isMeta 行（skill 正文、caveat、图片尺寸说明）归 other，但和以前一样不进 FTS，也就是 FTS 触发器不改。理由：这些是 harness 注入的，体积最大（2,200 万字符，比其余全部文本加起来还多），app 的搜索也不能变。
5. thinking 行的 `model`、`input_tokens`、`output_tokens` 照抄所在记录，和 reply 行一样；目前没有任何代码按 messages 汇总 token。
6. `cli.md` 的 `other` 定义改了两处（决定 6）：写明中断标记归 other；本地命令输出（`<local-command-stdout>`）在真实数据里有 111 条是 user 记录，回合规则把它算作人类输入，所以它是 prompt，不是原先写的 other。

## 踩过的坑

- app 的 `hiding_the_sorted_column_from_the_header_menu_keeps_the_selection_and_is_remembered` 在新 fixture 下失败：选中落到了 S2，应该是 S1。原因是隐藏列走 `AppRoot::update_columns`，只刷新表格、不通知它，按排序变化修正选中的 observer 不会运行，表格就停在原来的行号上。旧 fixture 下，S1 在 prompts 降序和默认顺序里碰巧都在第 1 行，所以测试一直通过。S3 的 prompt 数从 2 变成 4 后排到了 S1 前面，问题才暴露。临时换回旧的 S3、加调试输出确认了这一点，调试代码已删掉。
- `sqlite3 -readonly` 打不开 WAL 模式又没有 `-shm` 的库，要去掉 `-readonly`。
- 第一版对比脚本按段落切分，每个会话的标题行和命中行被空行分成两段，过滤不干净，得出一堆假 DIFF；改成 Python 按「标题 + 下一行」配对后，全部一致。
