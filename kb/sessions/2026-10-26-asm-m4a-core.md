## 概要

按总 plan 和 M4a spec 实现了直接读取 JSONL 的 `claude::conversation::read_conversation`，与索引解耦。读取完整文件、不设消息条数上限，保留真实输入回合、AUTO、compact、thinking、工具输入输出、过程文字和最终回复。工具结果通过 ID 配对，甚至可以回填前一回合；无调用的结果变成 `?` 工具步骤。对话模型只留下截断后的正文及原始长度，搜索命中在截断范围外时移动保留窗口。

共享了导出的 Record 和真实输入判断，没有改 TXT 导出行为。默认 `asm session` 输出不变，conversation 分支通过 transcript 定位直接读取，不创建 SQLite 索引。没有修改 `crates/app`、schema、`parse::RawRecord` 或 `parse::classify`。

## release 读取耗时

文件 `5f6eea99-2f43-4938-9035-b9db89173039.jsonl`，69,987,203 B，2 个真实回合、112 个工具调用。每种模式先运行一次预热，再取 5 次；时间是 `read_conversation` 调用本身，不含发现路径、输出打印或 GUI。

| 模式 | 首次计次 | 中位数 | 5 次范围 |
|---|---:|---:|---:|
| 无 matcher | 19.557ms | 20.043ms | 19.557–29.943ms |
| `--match 'image\|screenshot\|截图'`，6 个命中位置 | 20.590ms | 20.590ms | 20.107–21.216ms |

最初还测过 `cargo (test\|build)`，这个文件没有命中，记录在 `benchmark-initial.log`；最终数字使用有实际命中的查询。没有超过 core 150ms 预算，因此未添加更易误判记录类型的字节预过滤。首帧与转换开销留给后续 app 验收。

## 注意事项与自己的决定

- `read_conversation(path, matcher)`、模型字段和 `hit_places()` 按 spec，下一任务可以直接接入。`ToolLine.text` 只有字段值与高亮；description / command 的 `#` / `$` 前缀由使用方按 `ToolLineKind` 渲染，与现有工具行类型语义一致。
- `Matcher::pattern()` 返回包含大小写 flag 的有效表达式标识，例如 `(?i:needle)` 与 `(?-i:needle)`。这是对 spec 签名背后语义的补充：只返回 `Regex::as_str()` 会漏掉 RegexBuilder 的大小写选项，导致切换 Aa 后详情不重读。
- 同一条无 ID 的旧消息中的多个 text blocks 也合并；用内部记录序号区分不同无 ID 消息。真正 message ID 的多条记录仍按 ID 合并；工具与 thinking 阻断最终回复候选。
- 明确 `origin.kind != human` 且有正文时，即使 `isMeta` 也建立 AUTO；没有自动来源的 isMeta 注入仍丢弃。此项遵循 spec 分支顺序，真实数据证明不能把 isMeta 放到自动来源之前过滤。
- `stringify` 实际已经位于 `search/pyjson.rs`，所以把 `search/regex.rs` 的导入改为 crate 可见重导出，没有复制函数。
- 额外支持 MultiEdit 的 file_path 参数摘要；除此之外按 spec 工具字段规则。附件大小按 spec 的 base64 长度 × 3/4 估算，不解码、不扣 padding。
- 不因 `turn_duration` 结束 Conversation 回合，只累计 duration；TXT 导出仍保留原来的 turn_duration 结束逻辑。两者用途不同，未改变导出。
