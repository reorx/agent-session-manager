# 用量统计：删掉记录也不丢的用量账本，加一个按天看用量的 Usage 视图

## PRD

### 背景

用户想要一个单独的统计界面：今天一整天送进模型的 token 一共多少、按 API 价格值多少钱，近期每天的用量怎么变。现在应用只能按 session 看费用，回答不了「今天」和「每天」。

讨论中用户明确了最终要解决的问题：**今天产生的数据，明天把昨天及更早的 Claude Code session 记录全部删掉之后，统计数据仍然不会丢失。**

现在做不到。用量只存在索引里，而索引随时会从磁盘上的记录文件重建：改价格表、改解析、索引结构变化、手动 Rebuild、索引损坏、数据目录变化都会触发。重建只读磁盘上还在的文件，记录已被删掉的 session 的用量就没了。Claude Code 自己会清理 60 天前的记录（本机设置），用户也会手动删。2026-11-16 的索引里已有 65 个这样的 session（其中 56 个有用量），09-13 以前只剩 2,066 次调用、$428，而之后平均每天约 $180。

另外，应用只在启动和手动扫描时读新数据，关掉就不记了。记录文件如果在两次打开之间被删，那段用量从没被读到过。

### 目标

1. 用量一旦被应用读到，就永久留在一份单独的账本里；删记录文件、重建索引、索引损坏都不影响它。
2. 应用打开后常驻菜单栏，关掉窗口也照常定时读新数据，记录被删之前用量已经进了账本。
3. 应用里有一个 Usage 视图：选一段时间，看费用、token、调用数，按小时或按天的图，按模型、按项目、按 session 的分布；能从这里回到会话表看具体的 session。

### 各期共用的口径

这些口径在每一期都一样，各期 spec 不再重复。

- **用量日从本地时间 4:00 开始。** 「今天」是最近一个 4:00 到现在；凌晨 3 点做的事算在前一天。「本月」从当月 1 日 4:00 算起。会话表的时间预设（Today / 3 days / 7 days / 30 days / This month / Last month / Custom）用同一条规则，全应用只有这一种分日方式。首版写死 4:00，不可设置。
- **按每次 API 调用的时间归到小时和天，不按 session。** 一个 session 跨了三天，费用就分在三天里。所以 Usage 的数字和会话表按 session 合计的数字对不上：实测 11 月按 session 最后更新时间合计是 $2,883.66，按调用时间是 $2,756.90；10 月差 6%。这是口径不同，不是算错，Usage 视图里要写明。
- **「prompt token」就是 In**：未缓存输入 + 缓存写入 + 缓存读取，也就是每次请求送进模型的全部 token，和会话表的 In 列同一口径。实测某天 In 是 4.93 亿，其中 98.3% 是缓存读取，所以 In 总是和三段拆分一起显示，不单独给一个总数。
- **subagent 的用量算进它所属的 session**，和会话表一致（全部数据里占费用的 6.6%）。
- **费用由应用按 token 用量和官方价格表自己算**，和会话表一致。账本里存 token，不存费用；价格表改了，历史费用跟着重算，不用动账本。价格表里没有的模型，token 照计，费用记为 0，并提示有多少次调用没有价格。
- **账本只增不删。** 一次调用进了账本就一直在。记录文件被删、subagent 的记录被单独删、文件被重写，都不会让账本里的调用变少。所以某个 session 在账本里的用量可以比会话表显示的多（会话表在 subagent 记录被单独删掉时会扣掉那部分）。
- **界面文字**：Usage 视图和菜单栏的标签用英文，和现有工具栏、菜单一致；通知沿用中文。

### 分期

四期按顺序做，每一期单独实现、单独验收、单独合并。

| 顺序 | spec | 内容 |
|---|---|---|
| 1 | [usage-ledger](usage-ledger.md) | 用量账本：单独的文件，写索引的地方都同时记账；第一次启动从现有索引补齐；4:00 分日（含会话表的时间预设）；状态栏常驻今天的费用；应用开着时自动扫描 |
| 2 | [menubar-resident](menubar-resident.md) | 常驻菜单栏：关掉窗口不退出，后台照常扫描；菜单栏显示今天的费用，菜单里能重开窗口、立即扫描、退出 |
| 3 | [usage-view](usage-view.md) | Usage 视图：与会话表在同一个窗口里切换；时间范围与过滤；指标卡、主图、按 token 种类 / 模型 / 项目的拆分、费用最高的 session |
| 4 | [usage-drilldown](usage-drilldown.md) | 从 Usage 跳回会话表：选中某个 session；带着项目和「这段时间里有活动」的过滤去看有哪些 session |

第 1 期最先上线：它上线得越早，丢的历史越少。第 2、3 期都只依赖第 1 期，彼此独立；先做第 2 期是因为它直接关系到「不丢数据」。第 4 期依赖第 3 期。

界面稿是讨论前做的 Artifact：<https://claude.ai/artifact/HSkahb33aYAnvCTBpQ3Jbv>。它画的是 Usage 视图的布局和指标，各期 spec 与它不一致的地方以 spec 为准（它按 0 点分日、没有菜单栏常驻、标签是中文、视图切换写的是 `⌘1` / `⌘2`）。

### 各期都不做的事

- 不做 Claude Code hook，也不做开机自启。应用没开的那段时间靠下次打开时补读，记录文件只要还在就不丢。
- 不找回账本上线之前已经丢掉的历史（09-13 以前的用量、从 Time Machine 之类恢复）。
- 不做这些指标：星期 × 小时热力图、月底预估、换模型计价、主线与 subagent 的拆分、Prompt 数、缓存失效次数。
- 不做独立的 Usage 窗口、导出、清空或编辑账本、多台机器的账本合并。
- 不做「一天从几点开始」的设置项。
- 不改会话表按 session 计费的口径；会话表的 Cost 列和状态栏合计照旧。

### 验收标准

跨期的整体验收，在四期都合并之后做：

- 用一份测试用的数据目录跑应用，记下 Usage 里某几天的费用、In、Out、调用数。删掉这几天及以前的全部记录文件（含 subagent 的），先让应用扫描一次，再执行 Rebuild Index。Usage 里那几天的每个数字都不变，状态栏和菜单栏的今天费用也不变。
- 同一份数据，退出应用后删掉索引文件再启动（索引从头重建）。Usage 的数字仍然不变。
- 关掉窗口，往数据目录里加一个新 session 的记录文件，等到下一次后台扫描之后把它删掉，再从菜单栏重开窗口。Usage 里有这个 session 的用量，「费用最高的 session」里能看到它，点它时提示记录已被清理。
- 会话表选 Today，Usage 选 Today，两边的时间起点都是今天 4:00（凌晨 4 点前打开时是昨天 4:00）。
- 在 Usage 里点一个项目的跳转，会话表列出的 session 都在这个项目里、都在这段时间内有调用；清掉过滤后回到原来的列表。

## Tech Design

### 跨期的关键决定

- **账本是一个单独的 SQLite 文件，和索引在同一个目录**（`usage-ledger.sqlite`）。应用的索引（`index.sqlite`）和 `asm` 的索引（`index-cli.sqlite`，2026-11-16 起分开）在同一个目录，所以它们写的是同一份账本。`ASM_DB` 指到 `tmp/` 时账本也在 `tmp/`。
- **账本在 core 的 `Db` 里接上，不在 app 里。** 写索引的地方（app 的 store 线程、`asm` 各命令在查询前的扫描）都经过 `Db::insert_usage` / `Db::refresh_session_usage`，在这一层同时记账，谁写索引谁就记账，不会漏。
- **`Db` 另开一个连接写账本，不用 `ATTACH`。** `ATTACH` 的两个 WAL 库一起提交时，SQLite 不保证跨文件原子，提交顺序也不由我们控制；用两个连接可以固定「先提交账本，再提交索引」。这样崩溃只会留下「账本有、索引没有」，下次扫描重读同样的行再写一遍，结果相同。细节和被否决的做法在 [usage-ledger](usage-ledger.md)。
- **账本存什么**：每次 API 调用一行（主键和 token 列同索引的 `api_usage`，不存费用）；按「session × UTC 小时 × 模型 × fast × 长 prompt × 是否 subagent」的小时汇总（由调用表派生，可随时重算）；session 的项目、标题、类型、起止时间；项目的路径。实测 12.9 万次调用占 14 MB，小时汇总 5,510 行，一年约 115 万次调用、120 MB。
- **费用在读出来之后按当前价格表算。** 小时汇总的分组键含模型、fast、长 prompt，正是 `pricing::price_tokens` 需要的全部输入，所以从汇总重算和逐次调用计价的结果相同。改价格不用动账本，也不用为它提升索引的 `SCHEMA_VERSION`。
- **统计在主线程对内存里的小时汇总算。** store 线程启动时把整张小时汇总和 session 信息读出来发给界面，之后每次扫描只发有变化的 session；切时间范围、切过滤、出图都不再查库。这和「过滤排序在主线程」的现有规则一致。实测整表读出不到 1 ms，浏览器里对 3,534 个桶做一次全量聚合 2.7 ms。
- **分日规则只有一份**：core 的 `usage.rs` 提供「一个时刻属于哪个用量日」和「某个用量日从哪一刻开始」，会话表的时间预设、Usage 的范围、状态栏和菜单栏的今天都用它。
- **聚合逻辑放在 core（`usage.rs`），app 只画。** 这些是纯函数，按 BDD 先写测试；以后 `asm` 要出用量报表也能直接用。

### 各期的依赖与顺序

```text
usage-ledger ──┬── menubar-resident
               └── usage-view ── usage-drilldown
```

- usage-ledger 交付账本、分日规则、内存里的用量数据（`UsageData`）和状态栏的 Today。后面三期都读 `UsageData`，不再碰账本的写入。
- menubar-resident 把窗口的「关闭」改成「隐藏」，store 线程和定时扫描留在原处继续跑；菜单栏的数字来自 `UsageData`。它的菜单里的 Open Usage 一项要等 usage-view 合并后才加（写在 usage-view 的步骤里）。
- usage-view 加视图切换和整个 Usage 界面；状态栏的 Today 从这一期起可以点。
- usage-drilldown 给会话表加「这段时间里有活动」的过滤和从 Usage 过来的跳转。

### 风险与待定

- **价格表没有生效日期。** 费用按当前价格表算，Anthropic 以后调价时，调价前的用量也会按新价格显示。小时汇总带着时间，以后给价格表加生效日期就能分段计价，不用改账本。
- **同一次调用出现在两个 session 里会算两次。** resume 或 fork 出来的 session 会带着原来的调用记录。实测 12.9 万次调用里有 27 次这样的重复，合计 $2.71（总额 $12,965.70 的 0.02%），不处理。
- **半小时时区和夏令时。** 小时汇总按 UTC 整点存。4:00 分日在整点时区下是精确的；+5:30 这类时区，分日点落在一个桶的中间，这个桶整个归到后一天，会有半小时的偏差（用户在 +8，不受影响）。夏令时切换那天是 23 或 25 个小时，按天的数字是对的，按小时的图多一格或少一格。
- **账本上线前的重建。** 账本合并之前，任何一次索引重建都会丢掉已删 session 的用量。写这份 plan 时工作区里已有一项未提交的改动要把索引的 `SCHEMA_VERSION` 从 5 提升到 6，它合并后用新构建打开真实索引就会重建。`tmp/2026-11-12-usage-stats/index-copy.sqlite` 是 2026-11-16 的索引备份，账本上线并完成导入前不要删；[usage-ledger](usage-ledger.md) 的实施步骤 7 负责核对并从它导入。
