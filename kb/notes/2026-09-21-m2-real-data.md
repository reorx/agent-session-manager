# M2：界面接入真实数据（2026-09-21）

PRD 里程碑 M2。`crates/app` 不再有假数据（`fake.rs` 已删），表格、过滤、排序、详情 Metadata 全部来自 `crates/core` 的索引；冷启动时表格随索引流式填充。

## 数据流

```text
asm-store 线程（独占 Db）                      主线程（AppRoot）
Db::open → list_sessions ──Loaded──────────▶ set_rows（热启动到此表格可用）
Indexer::scan_streaming ──Progress/Session─▶ 状态栏进度 / upsert（冷启动靠它填表）
                        ──ScanDone─────────▶ 状态栏摘要、DB 大小
有改动则再 list_sessions ──Loaded──────────▶ set_rows（兜底，得到精确行）
StoreRequest::{Scan, Rebuild, Messages(id)} ◀─ Index 菜单、选中行
```

- `store.rs`：`Store::spawn(claude, db_path)` 起线程，返回请求端（`std::sync::mpsc`）与事件端（`async_channel`）。线程顶层把所有错误转成 `StoreEvent::Failed`，单个请求失败不会带走线程
- `main.rs` 的 pump：`recv().await` 拿到一条后 `try_recv` 把积压的全取出，一批只做一次 `upsert` + recompute + notify。冷启动 5488 条 `Session` 事件因此只触发几十次重算
- core 新增 `Indexer::scan_streaming(db, emit)` 与 `ScanEvent::{Progress, Session}`；`scan` 变成它的薄包装。每写一个 session 就 `db.session(id)` 读回再 emit，保证流出的行与索引一致（冷索引多花约 1–2%）。标记 missing 的 session 和 history 补位的 session 同样 emit
- `import_history` 现在跳过与索引里完全相同的 history session（原来每次扫描都重写全部 4547 条），所以"无变化的重扫"不再 emit 任何行，`ScanReport::history_sessions` 的含义变为"新写入或有变化的条数"

### 时序坑：项目路径滞后

没有 cwd 的空 session（fixture 的 S5）先于同项目的其他 session 写入时，流出的行 `project_path = None`，界面只能显示 `-Users-me-Code-alpha` 这样的编码名。两层处理：`project_entries` 用同 key 下任意一行的真实名字命名项目；扫描有任何改动时 `ScanDone` 后整表 reload 一次（5488 行 25ms）。

## 界面侧

- `model.rs`：`SessionRow::from_summary` 是 core → 界面的唯一转换点。预览文本单行化（`⏎`）并截到 240 字，Metadata 全文截到 2000 字，缺失值显示 `—` 且排序时取最小值（`started_at = i64::MIN`、`size = 0`）。`Kind::of`：history-only > BG > SDK（`entrypoint == "sdk-cli"`）> CLI
- 过滤：`Filter { project（project_key）, since_ms, show_empty }`。没有任何 prompt 的 session 默认隐藏（PRD R2.3 的"最少 prompt 数 ≥1"），View 菜单 "Show / Hide Sessions Without Prompts" 切换；Project 下拉的计数与 "All projects" 总数遵循同一开关
- 选中保持：`AppRoot::after_rows_changed` 在数据或过滤变化后按 session id 重新定位；找不到则选第一行，表空则清空。**扫描流式进行时不自动选中**——`TableState::set_selected_row` 自带滚动，首行一直在变，表格会跟着跳。启动时 `wanted_id`（来自 `state.json`）等到行出现或扫描结束
- 排序恢复：`delegate.set_sort(key, dir)` + `table.refresh(cx)`。`sync_column_arrows` 把 `self.sort` 写回 `Column::sort`，顺带修掉一个旧问题：点表头排序后一 resize（Preview 列宽同步会 `refresh`），箭头会被重置回 Updated
- `settings.rs`：`ViewState { mode, sort, project_key, range, show_empty, detail_visible, selected_id }`，`#[serde(default)]`，读不出来就用默认值。保存时机：`cx.observe(&table)` + 各 setter 里调 `persist`，与上次保存的快照相同则不写盘
- 详情面板：标题改为单行截断（两行标题会把 tab / chip 往下推 25px，点击脚本坐标失效）。Conversation 过渡实现：`Db::messages` 的 user / assistant 文本，`CONVERSATION_CAP = 300` 条、每条 4000 字——该视图还没虚拟化，全量渲染上千条会卡；M4 换成直接读 transcript + `v_virtual_list`
- dev profile：`agent-session-core`、`libsqlite3-sys`、`rusqlite`、`serde(_json)`、`memchr`、`rayon-core`、`chrono` 设 `opt-level = 3`。不设的话 debug 版 app 冷索引 7 秒以上还跑不完（SQLite 是 `-O0`）

## 实测（本机，debug 构建 + 上述 opt-level）

| 项 | 数字 |
|---|---|
| 数据量 | 941 个 transcript、1.27GB；5488 个 session（其中 4547 个 history-only，绝大多数来自 CodexBar 的 `ClaudeProbe` 目录）；索引 73MB |
| 热启动 | `AppRoot::new` 到 5488 行上屏 187–254ms（读索引 23–55ms）；之后增量扫描 0.07–0.66s |
| 冷启动 | 首批行约 1.0s 出现，全量 3.6–4.0s（解析 1.0s + 写库 2.3–2.6s + history 0.2s），期间表格可滚动 |
| 过滤 + 排序 | 5488 行 0–1ms |

"热启动"从 `AppRoot::new` 起算，不含进程启动与窗口创建。

## 测试

- core +3 个场景（`tests/index.rs`）：冷扫描流出的每一行与索引一致；重扫只流出变化的 session（追加、删除）；新 history 行只流一次
- app 24 个（`cargo test -p agent-session-manager`，纯逻辑、不起窗口）：`model`（行转换、Kind、过滤、项目列表、对话转换）、`table`（upsert、过滤与排序在新数据后保持、表头箭头）、`settings`（往返、损坏、旧文件缺字段）、`store`（直接用 core 的 fixture 目录：冷启动事件序列、热启动安静、Messages 请求、Rebuild、索引路径不可用时报 `Failed`）

## 相对 PRD 未做（留给后续）

设计稿的工具栏只有 Project / Scope / Updated / Preview 四个下拉，以下条目在设计稿里没有对应控件，M2 没有自行发明：

- R1：右键菜单、列显隐 / 列宽持久化、live 绿点、hover 提示
- R2：项目多选 / 可搜索（真实数据上百个项目，目前按最近活动排序 + 滚动）/ worktree 聚合；自定义日期区间、按 Started 过滤；"更多过滤"面板（Kind、工具、PR、subagent）；过滤 chip 与 Reset
- R5：行密度、相对时间、列顺序
- R12：状态栏的过滤 chip、搜索耗时（M3）

history-only 占了 83% 的行，Kind 过滤（或"隐藏 History"开关）在真实数据上的优先级比 PRD 预想的高。
