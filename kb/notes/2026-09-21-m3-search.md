# M3：界面搜索（2026-09-21）

PRD 里程碑 M3（R4）。搜索框接上了 core 的两条搜索路径：文本模式走 FTS5 索引，正则模式扫原始 transcript；表格出现 Matches 列与高亮片段，详情面板高亮命中并可逐个跳转。设计稿里没有搜索结果态，控件与配色是按 PRD R4 自行设计的（色值集中在 `style.rs` 的 Search 一节）。

## 数据流

```text
搜索框 Change ──150ms 防抖──▶ AppRoot::run_search
                               │ targets = 通过当前过滤条件的 session（新→旧）
                               ▼
asm-search 线程（search.rs，自带一条 query-only 连接）
  文本：fts::search（只在 targets 内）──Hits──▶ 表格 set_search / add_hits
  正则：regex::scan_sessions（逐批 32 个文件）──Hits…──▶ 同上，边扫边出
                                          ──Done──▶ 状态栏摘要 + 耗时
```

- 独立线程而不是复用 store 线程：搜索不会排在扫描或 `Messages` 请求后面。`Db::open_read_only` 是第二条连接（WAL 下读写并行），不建库、不迁移，首次文本搜索时才打开；查询出错就丢弃连接，下次重开
- 取代而非排队：`Searcher::search` 每次把 `latest` 加一；正则扫描按文件检查 `latest != seq` 后停止，旧 `seq` 的事件在 `on_search_events` 里丢弃。新搜索的第一条事件到达之前表格保留旧结果，不会每敲一个字闪一下
- "先过滤再搜"：搜索对象由界面给出，所以过滤条件变化、扫描后整表 reload 都会重搜一次；上限 `MAX_RESULT_SESSIONS = 200`（最新的 200 个），文本模式知道总数（"newest 200 shown"），正则扫描提前停止所以只说 "more match"

## core 的改动

- **两段式 FTS**（`fts::search`）：SQL 只 `GROUP BY session` 计数并用 `min(byte_offset)` 带出首条命中消息的 id，片段只给保留下来的 session 在 Rust 里算。原因是 FTS5 的 `snippet()` 会对每条命中消息重新做 trigram 分词——真实索引上 "the"（2165 条命中）167ms → 12ms，"error" 56ms → 8ms，而纯计数只要 3ms。`FtsQuery.sessions` 限定 session 集合，`FtsOutcome` 带回总 session 数 / 总命中数。`search_sessions` 保持原签名
- **`search::Matcher`**：文本模式 = 各词转义后的 `(?i)` 交替（长词在前），正则模式 = `compile_query`（非法正则按字面量）。片段、表格高亮、详情高亮共用它，app 不需要直接依赖 `regex`
- **`regex::scan_sessions`**：交互版扫描——每个文件计全部命中但只构造第一条的片段，逐批 emit，可取消，到 session 上限即停。原 `search` / `search_bytes` 行为不变（`make parity` 的基准）
- `Db::open_read_only` 用 `READ_WRITE` 标志 + `PRAGMA query_only`：`SQLITE_OPEN_READ_ONLY` 在最后一个写连接干净关闭（`-shm` 消失）后打不开 WAL 库

## 界面

- 工具栏：搜索框后面是 `.*`（正则，⌥⌘R）；正则模式下再出现 `Aa`（区分大小写，⌥⌘C）和「Labels ▾」多选（`thinking` / `tool_use` / `tool_use:Bash…` / `tool_result`）。选了标签会自动带上它所在的角色（`thinking` → assistant，`tool*` → tool），不受 Scope 影响。文本模式下 Scope 只剩 Tools 时状态栏提示需要正则模式
- 表格：`set_search(true)` 在 Preview 后插入可排序的 Matches 列（Preview 让出 64px），`set_search(false)` 移除；离开搜索时若正按 Matches 排序则回到默认顺序，该排序也不持久化。Preview 第二行变成「位置标签 + 高亮片段」，片段在首个高亮前最多留 12 个字符（单元格右侧截断，CJK 下 40 个字符就会把高亮挤出去）。顺带关掉了列选中（`col_selectable(false)`）：点表头会选中整列并盖掉行选中
- 详情：`DetailState` 保留原始 `MessageRow`，搜索变化时重新标记；chip 栏右侧 `▲ 2 / 9 hits ▼`，`cmd-g` / `cmd-shift-g` 全局可用，`n` / `shift-n` 只在表格有焦点时生效（绑定在 `DataTable` 上下文，不会吞掉搜索框里的输入）。当前命中橙色，其余黄色。消息改为滚动区的直接子元素，`ScrollHandle::scroll_to_top_of_item` 按子元素序号定位
  - 首个命中在第 300 条之后：窗口从命中前 5 条开始，`USER #n` 继续按真实序号计数，顶部说明跳过了多少条
  - 命中在单条消息 4000 字之后：截断位置移到命中前 200 字
  - 命中只在工具调用 / thinking 里（正则 + Tools）：Conversation 目前不显示这些内容，底部说明文字会指出，M4 直接读 transcript 后解决
- 键盘：搜索框 Enter = 立即搜索并把焦点交给表格；Escape = 清空搜索、回到表格（不再用 `clean_on_escape`，Input 会把 Escape 冒泡上来）
- 持久化：`ViewState.search`（模式、大小写、Scope、Labels），查询本身不保存

## 实测（本机，debug 构建的 app，5497 个 session / 950 个 transcript）

| 项 | 数字 |
|---|---|
| 文本搜索 "session table"（94 个 session） | 首次 33–40ms（含打开连接），之后 7ms |
| 文本搜索 "gpui" | 2–6ms |
| 两字 CJK "搜索"（LIKE 路径，118 个 session） | app 内 83–137ms；release 的 `asm` 14–27ms |
| 正则 `cargo (test\|build) -p`，User + Assistant | 热缓存 240–310ms |
| 同上 + Tools | 热缓存 380–425ms |
| 正则首次扫描（文件缓存是冷的） | 1.6s |

对照验收标准：FTS <100ms ✅；正则 <500ms ✅（热缓存，PRD 的口径）；CJK 两字可搜 ✅，但 debug app 里 LIKE 路径贴着 100ms，见下。

## 已知问题与未做

- 两字查询走 `LIKE '%…%'` 全表扫 70MB 文本，是目前最慢的文本查询。可选方案：给 1–2 字查询另建 bigram 索引，或直接在内存里扫（未做）
- 正则冷扫描 1.6s：第一次要把 1.27GB 读进页缓存；结果是流式出现的，所以首批行远早于结束
- 详情面板里看不到工具调用内的命中（M4）
- 真实按键只验证过 Enter → 表格焦点 → `n`（`tmp/focus-probe/after-n.png`）；Escape 清空只经 autoplay 调用的同一个 `clear_search` 验证过，没有用真实按键确认

## 验收

`make screenshot-search` → `tmp/2026-09-21-m3-search/`：`1-text-search` … `7-cleared` 七张。脚本用 `ASM_SEARCH_AUTOPLAY=1` 让 app 自己走完搜索流程，每步稳定后打印 `autoplay-search: <step>`，脚本据此按窗口 ID 截图——不发按键、不点击、不碰剪贴板。

教训：第一版脚本用 System Events 发全局按键 + 剪贴板粘贴，按键只进最前台的 app，人在用机器时会打进别的窗口；cliclick 的 `kp:return` / `kp:esc` GPUI 也收不到。另外程序化 `InputState::set_value` 不发 `Change` 事件，autoplay 里要自己调 `run_search`。
